Type-surface parity matters because `dist/index.d.ts` is published: a changed declaration is a
public API change for TypeScript consumers even when the runtime behaviour is identical.

Two packaging facts are **not** parity-checkable here and must be handled at graduation:

1. **A new runtime dependency.** C imports alien-signals, so `libs/signal/package.json` gains a
   `dependencies` entry and the root `catalog` gains a pin; the published package stops having zero
   dependencies. B adds nothing. This is the only respect in which C is not a drop-in *package* even
   though it is a drop-in *API*.
2. **CDN / raw-entry resolution.** The raw `index.js` is the `import`/`module` entry. With C it
   contains a bare `alien-signals` specifier, which a browser cannot resolve without an import map;
   the bundled `esm`/`cjs` entries inline it and are unaffected. Mitigation is a README note plus
   making the bundled entry the documented CDN one.

## 5. What a drop-in verdict does *not* claim

* It does not claim identical *performance*: C costs +90 % on a raw write+read microbenchmark (each
  read consults the alien node when a subscriber is active) while being within ~14 % on the
  long-lived-component macrobench. See `RESULTS.md`.
* It does not claim identical *internals*: `prepareSignal` still returns
  `{ $signal, fireChanged, listeners, setValue }` with the same semantics, but in C the storage is an
  alien node. Code that writes to the underlying node behind the wrapper's back would desynchronise
  the `===` shadow — nothing in the repo does that.
* It does not claim the new computed axis is available in the baseline sense: in C, `$C` is an alien
  computed, so it follows alien's rules (pull-based, read-only, no eager mode except `$CE`).
